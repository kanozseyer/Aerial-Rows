# AI Handoff Export Process v3

This is the canonical procedure for exporting the Launcher/Aerial-Rows research and conversation context into GitHub without losing bytes or making partial progress hard to recover.

## Goals

- Preserve every research report byte-for-byte.
- Make the archive readable by humans and machine-verifiable by any AI/model.
- Avoid large fragile tool payloads.
- Make every batch resumable.
- Never modify application source while performing the documentation export.
- Prevent concurrent branch changes from being overwritten.

## Canonical report format

Every raw report has a `*.manifest.json` with:

- `schema_version`
- report ID / collection
- original source filename
- original byte size
- original SHA-256
- ordered part list
- each part's byte size
- each part's SHA-256
- each part's Git blob SHA-1
- an explicit statement that reassembly is byte-exact

Reassembly rule:

> Concatenate part files in manifest order with **no separator**.

## Canonical export workflow

1. Read `docs/ai-handoff/EXPORT_STATUS.md` and `docs/ai-handoff/raw/ARCHIVE_MANIFEST.json`.
2. Work on one report/subgroup at a time.
3. Run `chunk_report.py` locally against the original report.
4. Verify the generated manifest reconstructs the source exactly.
5. Create exact Git blobs from the generated bytes. Base64 blob creation is preferred for raw report parts because it avoids newline/text-normalization ambiguity.
6. Build one Git tree containing all files for the batch.
7. Create one commit from the current branch head.
8. Move `aerialrows-development` with a compare-and-swap `expected_sha` lease. If the branch moved, stop, inspect, rebase/rebuild the tree, and retry; never force over unknown work.
9. Run `python docs/ai-handoff/tools/validate_archive.py` locally or via GitHub Actions.
10. Update `EXPORT_STATUS.md` only after validation succeeds.

## Why v3 replaced the earlier methods

### Initial attempt

The first attempt staged very large archive blobs before creating a final tree/commit. Progress looked stuck and recovery was poor.

### v1 / v2 Contents API approach

The recovery process switched to many small `create_file` commits. This was durable but slow and exposed newline-boundary mistakes. C4/C5 required manual newline repair, and a later retroactive audit discovered C3 part 3 was still one byte short despite a prior checkpoint claiming exact reconstruction.

### v3 Git-object approach

The Git connector exposes raw blob, tree, commit and ref-update operations. v3 uses those directly, giving:

- byte-exact blobs;
- one atomic commit per batch;
- fewer network/tool calls;
- no half-committed report;
- compare-and-swap branch safety;
- deterministic Git blob hashes recorded in manifests;
- automated repository validation.

## Chunking guidance

Default target: about 14 KiB per part. Smaller reports can remain a single file. Exact byte preservation matters more than pretty boundaries.

The chunker prefers newline boundaries for readability but never changes bytes.

## Validation

Run:

```bash
python docs/ai-handoff/tools/validate_archive.py
```

The validator checks every report marked `complete` in the master raw archive manifest:

- all parts exist;
- part byte sizes match;
- part SHA-256 values match;
- computed Git blob SHA-1 values match;
- concatenated byte size matches the original;
- concatenated SHA-256 matches the original.

A GitHub Actions workflow runs the same validator whenever the handoff archive changes.

## Failure/recovery rule

If the conversation/tool/environment fails:

1. inspect the live `aerialrows-development` head;
2. read `EXPORT_STATUS.md`;
3. run the validator;
4. continue only the first pending report/subgroup;
5. never redo a validated complete report unless its manifest fails;
6. never trust a prose checkpoint over the machine validator.

## Security / repository hygiene

Do not commit:

- the proprietary Projectivy APK;
- decompiled proprietary source;
- REA binaries;
- JADX binaries;
- signing material;
- unrelated private files.

Commit only the clean-room findings, process/provenance notes and open-source Aerial-Rows project material.
